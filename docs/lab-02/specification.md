# Lab 2 Sprint Engineering Specification — TokTickIT Requester Ticketing MVP

## 1. Sprint Goal

Deliver a professional, responsive Requester-facing ticketing experience for TokTickIT: a Development Requester can select a testing identity, create an IT support ticket with attachments, receive a backend-generated official Ticket Number, and manage their own tickets (list, search, filter, sort, paginate, view detail, add/remove attachments) — while being prevented from accessing any other Requester's data.

## 2. Stakeholder Request Interpretation

The IT department is ready to accept real support requests and needs a working end-user experience before real login exists in Lab 3. A Requester must be able to describe a problem (summary + description), classify it (Category, Related System), set a Requested Priority, attach supporting evidence, and submit. After submission the Requester must find their tickets again easily and manage permitted attachments on them. The system generates the official Ticket Number, stores data safely, and strictly isolates each Requester's data from other Requesters. Until authentication arrives, a clearly-labeled temporary Development Requester Selection screen simulates "who am I" for testing purposes only.

## 3. Scope

### Included
- Development Requester Selection screen (dropdown of active seeded requesters) and Change Requester behavior.
- Create Ticket screen: classification fields, Summary, Description, Requested Priority, initial Attachments; backend-generated Ticket Number and Ticket Date.
- My Tickets screen: owned, paginated list with search, filtering, sorting, pagination, loading/empty/no-results/failure states.
- Requester Ticket Detail screen (read-only header) with Attachment lifecycle: upload, metadata, download, soft removal with reason.
- Ownership protection enforced by the backend for every ticket/attachment access.
- Zen Green Theme UI foundation: reusable form, list, badge, validation, loading, empty, error conventions and responsive layouts.
- PostgreSQL schema increment (DevelopmentRequester, Ticket, Attachment, RelatedSystem; existing Category retained) plus idempotent seed data.

### Explicitly Excluded
- Authentication and security: login, logout, passwords, hashing, sessions, tokens, real role-based authorization. The Development Requester selector is NOT authentication.
- IT Staff workflow: dashboard/queue, claiming or reassigning tickets, setting IT Priority, ticket ownership transfer.
- Collaboration/work tracking: Public Comments, Internal Notes, Actions Taken.
- Ticket lifecycle after creation: any status change beyond the initial `New` status (resolve, close, reopen, cancel).
- Administration: user/reference-data management screens.

## 4. Functional Requirements

- **FR-01** The system shall load active Categories, active Related Systems, and active Development Requesters from PostgreSQL via REST APIs for use as reference data.
- **FR-02** The system shall provide a Development Requester Selection screen listing only active Requesters, with loading, empty, and API-failure states.
- **FR-03** After selection, the application shell shall display the selected Requester's name and offer a Change Requester action; changing the selection shall reload requester-specific data.
- **FR-04** The system shall allow the selected Requester to create a Ticket providing Category, Related System, Summary, Description, Requested Priority, and optional initial Attachments.
- **FR-05** On successful creation, the backend shall generate a unique official Ticket Number and a Ticket Date, persist the Ticket with status `New`, and return the saved values to the UI.
- **FR-06** The system shall validate all Ticket input on both the frontend and the backend and display field-level messages near the associated fields.
- **FR-07** The system shall provide a My Tickets screen listing only the Tickets owned by the selected Requester, with search, filters, sorting, and pagination driven by query parameters.
- **FR-08** The system shall provide a Requester Ticket Detail screen showing one owned Ticket's information read-only.
- **FR-09** The system shall allow the owning Requester to upload permitted Attachments to their own Ticket (type/size/count rules in BR-14).
- **FR-10** The system shall retrieve Attachment metadata, download active Attachments, and soft-remove Attachments with a required reason.
- **FR-11** Every ticket and attachment retrieval/modification endpoint shall enforce that the resource belongs to the currently selected Development Requester.
- **FR-12** The UI shall handle loading, success, validation-failure, submission-failure, empty-result, no-results, and API-failure states visibly on every screen, including responsive mobile/tablet layouts.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique.
- **BR-02** A new Ticket begins with Current Status `New`.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04** A Development Requester must be selected before any ticket screen can be used; without a selection the app shows the Requester Selection screen.
- **BR-05** The selector lists only active Requesters; inactive Requesters never appear.
- **BR-06** When the selected Requester changes, all requester-specific data must be reloaded.
- **BR-07** Ticket Date is a system-generated timestamp recorded at creation time.
- **BR-08** `requesterId` is bound to the Ticket at creation and can never change.
- **BR-09** The backend must enforce selected-requester ownership; an ownership mismatch returns the documented safe response (see api-spec.md).
- **BR-10** Ticket Summary is required and must contain 5–120 characters after trimming leading and trailing whitespace. Description is required and must contain 20–2,000 characters after trimming. These constraints must be validated by both the frontend and the backend.
- **BR-11a** Category and Related System must be values from active reference data; validity must also be checked by the backend.
- **BR-11b** Requested Priority must be one of the allowed enum values (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`); validated by both frontend and backend.
- **BR-12** While a Ticket submission request is being processed, the Submit button must display a busy state and remain disabled, preventing repeated submission through the UI.
- **BR-13** If submission fails, entered form values must be preserved and a safe error message shown.
- **BR-14** Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF. Maximum size is 5 MB per file. Maximum five active Attachments per Ticket.
- **BR-15** Attachment removal must use soft removal only.
- **BR-16** A non-empty removal reason is required when removing an Attachment and must be retained as removal metadata.
- **BR-17** A removed Attachment remains visible as metadata but cannot be previewed or downloaded.
- **BR-18** If Ticket creation succeeds but one or more initial Attachment uploads fail, the Ticket and all successfully uploaded Attachments remain saved. A failed upload must not create an active Attachment record. The failed file must be reported to the Requester, who may retry the upload from Ticket Detail.
- **BR-19** Search, filtering, and sorting operate only on the selected Requester's Tickets. Search performs a case-insensitive partial match on Ticket Number or Ticket Summary; Description is not a My Tickets search target because it is not displayed in the list.
- **BR-20** Pagination defaults to page 1 and page size 10; permitted page sizes are 10, 20, and 50. The query contract is strict: unknown parameter names and invalid known parameter values both return HTTP 400.
- **BR-21** My Tickets defaults to `updatedAt DESC`, with Ticket ID DESC as the deterministic secondary sort.
- **BR-22** My Tickets shows an empty state when the selected Requester owns no Tickets, and a distinct no-results state when Tickets exist but none match the current search or filters.
- **BR-23** Ticket Detail may be retrieved only when the requested Ticket belongs to the selected Development Requester.
- **BR-24** The Development Requester mechanism is temporary and must be replaceable by authenticated requester identity in Lab 3 without changing Ticket ownership relationships.

## 6. UI Specification Summary

- **Application shell**: TokTickIT identity, My Tickets navigation, Create Ticket navigation, selected Requester identity display, clear active-page indication, responsive mobile navigation.
- **Requester Selection screen**: title, explanation that this is a Lab-2-only testing mechanism, dropdown loaded from PostgreSQL, Continue button, loading/empty/failure states, keyboard accessible (full layout in ui-spec.md).
- **Create Ticket screen**: system-generated/read-only fields visually distinct at top, classification fields grouped, Summary/Description given sufficient width, Attachments below main fields, primary Submit (busy/disabled states) and secondary actions at bottom; field-level validation messages under fields; required fields marked with red asterisk; success state displays the generated Ticket Number (full layout in ui-spec.md).
- **My Tickets screen**: Ticket Number/Summary search, suitable filters, accessible sorting controls, Clear Filters + Create Ticket actions, pagination, desktop sortable table / mobile card representation, row/card navigation to Ticket Detail, and loading/empty/no-results/failure states (full layout in ui-spec.md).
- **Ticket Detail screen**: read-only ticket header, distinct Attachment section with active/uploading/invalid/removed/unavailable states, download and soft-remove actions (soft removal via confirmation modal with mandatory reason — full layout in ui-spec.md).
- **Zen Green Theme**: primary #006B3C, secondary #0B7A46, pale green #EAF6EF, background #F5F7F6, white surfaces, dark charcoal-green text, dark red errors below fields, amber warnings, green success not relying on color alone.
- **Responsive**: ≥992px multi-column centered; 768–991px two-column where practical; <768px stacked vertical, touch-friendly buttons, no horizontal scrolling; no clipping/overlap at any size.

## 7. Data Changes

Concepts: **DevelopmentRequester**, **Ticket**, **Attachment**, **Category**, **RelatedSystem**.

### Ticket

| Field | Type | Constraints |
|---|---|---|
| id | Int | PK, autoincrement |
| ticketNumber | String | Unique; backend-generated `{YY}{MM}-{4 digits}`, sequence resets monthly |
| requesterId | Int | FK → DevelopmentRequester, not null, immutable (BR-08) |
| categoryId | Int | FK → Category, not null |
| relatedSystemId | Int | FK → RelatedSystem, not null |
| summary | String | 5–120 chars after trimming (BR-10) |
| description | String | 20–2,000 chars after trimming (BR-10) |
| requestedPriority | Enum | `LOW \| MEDIUM \| HIGH \| CRITICAL` (BR-11b) |
| currentStatus | Enum | `NEW` — initial status only in Lab 2 (BR-02) |
| ticketDate | DateTime | UTC, generated at creation (BR-07); displayed in Asia/Bangkok (UTC+7) |
| createdAt / updatedAt | DateTime | UTC |

### Attachment

| Field | Type | Constraints |
|---|---|---|
| id | Int | PK, autoincrement |
| ticketId | Int | FK → Ticket, not null |
| originalFilename | String | Not null; client-provided name kept as metadata |
| storedFilename | String | Unique sanitized generated name |
| mimeType | String | JPG/JPEG, PNG, WEBP, or PDF only (BR-14) |
| sizeBytes | Int | ≤ 5 MB per file (BR-14) |
| removedAt | DateTime | Nullable timestamp — **source of truth** for soft removal; non-null means removed (BR-15/BR-17) |
| removedReason | String | Nullable; required when removedAt is set (BR-16) |
| createdAt | DateTime | UTC |

### DevelopmentRequester
`id` (PK), `name`, `email` (unique), `isActive` (Boolean), `createdAt`

### Category (evolved from Lab 1)
Retains the existing Lab 1 `Category` entity. Lab 2 adds `isActive` (Boolean, default true) through a Prisma migration that backfills all existing Category rows as active (`isActive = true`). Subsequent required Category data and active states remain the responsibility of the Lab 2 idempotent seed (`Account and Access`, `Hardware`, `Software`, `Network`).

### RelatedSystem (new in Lab 2)
`id` (PK), `name` (unique), `isActive` (Boolean), `createdAt`

Relationships:
- One Requester owns many Tickets; one Ticket belongs to exactly one Requester (FK `requesterId`).
- One Ticket has many Attachments; one Attachment belongs to one Ticket (FK `ticketId`).
- Many Tickets may reference one Category; many Tickets may reference one Related System (FKs).

Constraints and indexes:
- `Ticket.ticketNumber` unique; `Category.name` unique; `RelatedSystem.name` unique.
- FK indexes on `requesterId`, `categoryId`, `relatedSystemId`; index on `Ticket.updatedAt` to support default sorting.
- Soft removal represented solely by nullable `removedAt` (+ required `removedReason`) on Attachment; no redundant boolean flag.
- Active filtering uses the `isActive` flag on DevelopmentRequester, Category, and RelatedSystem.
- Evolution to Lab 3: adding an authenticated User model will link identity to the existing `requesterId` relationship without altering Ticket ownership structure (BR-24).

Seed data (idempotent, safe to run repeatedly):
- Four Categories: Account and Access, Hardware, Software, Network.
- At least six Related Systems (e.g., Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer).
- At least four active Development Requesters and at least one inactive Development Requester.

At least one database-design decision justified: see Section 11 (Assumptions and Decisions).

## 8. API Contract

REST endpoints (full shapes, validation, statuses, and errors defined in [api-spec.md](./api-spec.md)):

| Capability | Method & Path (indicative) |
|---|---|
| Active Categories | GET /api/categories |
| Active Related Systems | GET /api/related-systems |
| Active Development Requesters | GET /api/requesters |
| Create Ticket | POST /api/tickets |
| Owned Ticket list (search/filter/sort/pagination) | GET /api/tickets |
| One owned Ticket | GET /api/tickets/:id |
| Upload Attachment | POST /api/tickets/:id/attachments |
| Attachment metadata | GET /api/attachments/:id |
| Download active Attachment | GET /api/attachments/:id/download |
| Soft-remove Attachment | POST /api/attachments/:id/remove |

Ticket and Attachment requester-scoped endpoints enforce selected-requester ownership (BR-09). Successful creation returns 201 with backend-generated Ticket Number. Invalid input returns 400. Attachment soft removal uses `POST /api/attachments/:id/remove` with a JSON body `{ reason }`; no DELETE endpoint is exposed for attachments. Missing resources and ownership mismatches return the documented safe response. Unexpected server failures return a safe generic 500 response without internal details.

## 9. Acceptance Criteria

Creation and validation:
- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02** Given Summary shorter than 5 or longer than 120 characters, when submitted, then a field-level message appears and the form is not submitted; if the validation is bypassed at the API level, the backend returns 400.
- **AC-03** Given Description shorter than 20 or longer than 2,000 characters after trimming, when submitted, then a field-level message appears and the form is not submitted; if the validation is bypassed at the API level, the backend returns 400.
- **AC-04** Given Category or Related System not present in active reference data, when POST /api/tickets is called, then the backend rejects it with 400. Given Requested Priority not in the allowed enum values, the backend also rejects it with 400.
- **AC-05** Given a submission in progress, when the user attempts to click Submit again, then the button is disabled/busy so no duplicate submission request is sent through the UI.

Requester context:
- **AC-06** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-07** Given the selector is open, when it loads, then inactive Requesters do not appear in the dropdown.
- **AC-08** Given a Requester switch, when the new selection is confirmed, then requester-specific data (My Tickets, shell identity) reloads for the new Requester.
- **AC-09** Given zero active Requesters exist, when the selector loads, then a clear empty state is displayed; given the API fails, a safe failure state is displayed.

Ownership:
- **AC-10** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (documented safe response).
- **AC-11** Given Requester B is selected, when My Tickets loads, then none of Requester A's Tickets appear.

My Tickets list:
- **AC-12** Given the selected Requester's Tickets whose Ticket Number or Summary contain the search term (case-insensitive partial match), when searching, then matching tickets are returned; a term present only in Description does not match.
- **AC-13** Given a filter (e.g., Category) is applied, when the list loads, then only matching Tickets appear.
- **AC-14** Given a sort choice, when applied, then ordering matches the documented contract; default order is updatedAt DESC, id DESC.
- **AC-15** Given more Tickets than one page size, when paginating, then correct pages and metadata (total count, total pages) are returned.
- **AC-16** Given an invalid page number, an invalid page size, an unknown query parameter name, or an invalid known parameter value, when requested, then the API returns 400.
- **AC-17** Given the Requester owns no Tickets, when My Tickets opens, then an empty state is shown distinct from the no-results state shown when filters exclude everything.

Attachments:
- **AC-18** Given a permitted file ≤5 MB and fewer than 5 active Attachments, when uploaded, then the Attachment becomes active with retained metadata.
- **AC-19** Given a disallowed type or a file >5 MB, when uploaded, then a safe rejection message appears and no active record is created.
- **AC-20** Given 5 active Attachments already exist, when another upload is attempted, then it is rejected safely.
- **AC-21** Given an owner removes an Attachment with a non-empty reason, when removal completes, then the Attachment remains visible as metadata but cannot be downloaded or previewed.
- **AC-22** Given removal attempted without a reason, when submitted, then removal is rejected until a reason is provided.
- **AC-23** Given Ticket creation succeeded but an initial upload failed, when the flow completes, then the Ticket stays created with successful uploads saved, the failure is reported, and retry is available from Ticket Detail.
- **AC-24** Given Requester B is selected, when directly requesting an Attachment belonging to Requester A, then access is rejected with the documented safe response.

States and responsiveness:
- **AC-25** Given the backend is unavailable, when any screen loads its data, then a safe error state appears.
- **AC-26** Given the backend is unavailable or submission fails, when the Requester submits Create Ticket, then a safe error message appears and entered form values are preserved.
- **AC-27** Given desktop, tablet, and mobile viewports, when any screen renders, then layouts follow ui-spec.md with no clipped labels, overlap, or horizontal page scrolling.
- **AC-28** Given a keyboard-only user, when navigating the Requester Selection, Create Ticket, My Tickets, Ticket Detail, and Attachment removal modal, then all interactive controls are reachable and operable with visible focus indicators and accessible labels.

## 11. Assumptions and Decisions

1. **Database design justification**: soft removal is modeled using a nullable `removedAt` timestamp (source of truth, no redundant boolean flag) and `removedReason` on the Attachment row rather than deleting rows, so removal metadata (reason, date) survives for audit and the storage file handling can be deferred safely; unique `ticketNumber` is enforced at the DB level because BR-01 uniqueness must hold under concurrency.
2. **Ticket Number format** (implementation decision, not a business rule): `{YY}{MM}-{4-digit sequence}` generated inside the creation transaction; the 4-digit sequence **resets monthly**, consistent with the `YYMM` prefix. The monthly sequence ranges from `0001` to `9999`. If the monthly sequence is exhausted, Ticket creation must fail safely rather than generating a duplicate Ticket Number.
3. **Ticket Date storage and display**: stored as UTC timestamps in the database (not bound to any timezone); displayed to users in the Asia/Bangkok (UTC+7) local timezone.
4. **Stored filename sanitization/rename** (security implementation decision): uploads are renamed to generated safe names to prevent path traversal and name collisions; original filename kept as metadata.
5. **Attachment removal confirmation** (UI decision): removal requires an explicit confirmation modal containing a mandatory non-empty reason field; the removal is applied only after confirmation.
6. **Selected-requester context transport**: the client sends the selected `requesterId` explicitly on requester-scoped requests during Lab 2; this is understood to be spoofable precisely because it is not authentication (BR-03) and is replaced in Lab 3 (BR-24).
